# Stringee Flutter Call Sample

This sample demonstrates a production-oriented one-to-one call flow using
`stringee_plugin` on Android and iOS.

It includes:

- Access-token input, persistence, automatic reconnect, and logout
- Incoming and outgoing calls
- Voice and video with both `StringeeCall` and `StringeeCall2`
- Android FCM incoming-call notifications and an in-call foreground service
- iOS PushKit and CallKit integration
- Call timeout, response validation, duplicate-call protection, and safe cleanup

## Requirements

- Flutter with Dart `>=3.3.4 <4.0.0`
- A Stringee project and an access token generated by a trusted server
- A Firebase project for Android FCM
- A real iOS device for PushKit/CallKit incoming-call testing

Never generate Stringee access tokens from an API secret inside the Flutter application. API
secrets must remain on a trusted server.

## Setup

### Install dependencies

```shell
flutter pub get
```

### Configure Firebase with FlutterFire

Install the FlutterFire CLI and ensure the global Dart executable directory is on `PATH`:

```shell
dart pub global activate flutterfire_cli
export PATH="$PATH:$HOME/.pub-cache/bin"
```

From this directory, configure the Android and iOS apps:

```shell
flutterfire configure --platforms=android,ios
```

Select the intended Firebase project. FlutterFire generates or updates:

- `lib/firebase_options.dart`
- `android/app/google-services.json`
- `ios/Runner/GoogleService-Info.plist`
- `firebase.json`

If FlutterFire reports `cannot load such file -- xcodeproj`, install the Ruby `xcodeproj` gem and
run `flutterfire configure` again.

For Android, upload the FCM credentials required by Stringee in the Stringee dashboard. For iOS,
configure APNs/VoIP credentials, enable Push Notifications, and enable the required Background
Modes in Xcode.

### Run the sample

```shell
flutter run
```

Paste a valid Stringee access token into the app and tap **Connect**.

## Connection and session flow

`StringeeWrapper` owns one `StringeeClient` for the application process.

1. `initialize()` creates the client and subscribes to native Stringee events.
2. `connect(token)` trims and persists the token, then connects the client.
3. On the next app launch, the saved token is restored and the client reconnects automatically.
4. After `didConnect`, the sample registers the current FCM or PushKit token with Stringee.
5. When Stringee requests a new access token, the saved token is cleared and the UI asks the user
   to enter a replacement.
6. `logout()` unregisters push, clears saved call/push state and the access token, then disconnects.

`disconnect()` is intended for ending the current connection. `logout()` additionally removes the
persisted session so the app cannot reconnect automatically.

## Four outgoing-call cases

The main screen exposes these four independent cases:

| API | Media | Wrapper method |
| --- | --- | --- |
| `StringeeCall` | Voice | `makeVoiceCall()` |
| `StringeeCall` | Video | `makeVideoCall()` |
| `StringeeCall2` | Voice | `makeVoiceCall2()` |
| `StringeeCall2` | Video | `makeVideoCall2()` |

Example:

```dart
final stringee = StringeeWrapper();

await stringee.makeVoiceCall(to: calleeId);
await stringee.makeVideoCall(to: calleeId, videoQuality: VideoQuality.hd);
await stringee.makeVoiceCall2(to: calleeId);
await stringee.makeVideoCall2(to: calleeId, videoQuality: VideoQuality.hd);
```

An outgoing call is accepted only when the client is connected, the callee ID is not empty, and
there is no other active SDK or CallKit call.

## Call lifecycle safeguards

The wrapper packages the lifecycle shared by `StringeeCall` and `StringeeCall2`:

- Only one active call is allowed. A second incoming call is rejected while another call exists.
- Every SDK response from `makeCall`, `initAnswer`, `answer`, `reject`, and `hangup` is checked
  before the state advances.
- The default 60-second timer ends a call that never reaches the started state.
- A call becomes **started** only after both signaling is `answered` and media is `connected`.
- iOS answer waits for an active CallKit audio session, but stops at the timeout or immediately when
  the call is cleared. An ended call cannot be answered later by a delayed callback.
- End handling is idempotent. Repeated UI, notification, SDK, or CallKit end events clear the same
  model only once.
- When the SDK already reports `ended` or `busy`, the wrapper clears local state without issuing an
  unnecessary second Stringee `hangup` or `reject`.
- Timers, audio listeners, call-event subscriptions, notifications, foreground services, and video
  views are released during cleanup.

For Android video, use `stringee_plugin` `1.3.2` or newer. It safely handles the short interval in
which a `StringeeCall2` remote renderer can become unavailable while its video track is replaced.

## Incoming-call notifications

### Android

Android uses Firebase Cloud Messaging and `flutter_local_notifications`.

- The Firebase background handler parses Stringee data messages while the app is backgrounded or
  terminated.
- A `started` push shows a high-priority incoming-call notification with **Answer** and **Reject**.
- Terminal statuses such as `ended`, `busy`, or `agentEnded` remove stale call UI and notification
  state.
- Notification actions are stored briefly and reconciled with the SDK call after the Flutter UI is
  ready.
- Reject can be processed by a background Stringee client using the locally saved access token.
- Answer opens the call UI and requests camera, microphone, and Bluetooth permissions as required.
- An ongoing foreground-service notification keeps an active call alive in the background. Its
  chronometer starts only after signaling is answered and media is connected.
- Android 13 or newer requires notification permission. Recent Android versions may also require
  full-screen intent permission.

The app must connect to Stringee as soon as possible after startup so an incoming SDK call can be
matched with its notification action.

### iOS

iOS uses PushKit for VoIP pushes and CallKit for the system call UI.

- Test incoming calls on a real device; the complete PushKit/CallKit flow is not available on the
  simulator.
- The VoIP token is registered with Stringee after the client connects.
- Incoming calls are reported to CallKit before they are presented in Flutter.
- Answer waits for CallKit to activate the audio session before calling `initAnswer()` and
  `answer()` on Stringee.
- End, mute, outgoing-connected, and handled-on-another-device events are synchronized with
  CallKit without ending the Stringee call twice.

See [Stringee Push Notification for Flutter](https://developer.stringee.com/docs/push-notification/flutter)
for dashboard and platform credential setup.

## `StringeeWrapper` API

### Initialization and connection

```dart
void initialize({
  List<StringeeServerAddress>? serverAddresses,
  String? baseAPIUrl,
})

Future<void> connect(String token)
Future<void> disconnect()
Future<void> logout()
Future<String> getSavedAccessToken()
Future<void> clearSavedAccessToken()
```

### Push registration

```dart
Future<void> registerPush({bool? isProduction, bool? isVoip})
Future<void> unregisterPush()
```

When `isProduction` is omitted on iOS, the sample uses `kReleaseMode`.

### Calls

```dart
Future<void> makeVoiceCall({
  String? from,
  required String to,
  Map<dynamic, dynamic>? customData,
})

Future<void> makeVideoCall({
  String? from,
  required String to,
  Map<dynamic, dynamic>? customData,
  VideoQuality? videoQuality,
})

Future<void> makeVoiceCall2({
  String? from,
  required String to,
  Map<dynamic, dynamic>? customData,
})

Future<void> makeVideoCall2({
  String? from,
  required String to,
  Map<dynamic, dynamic>? customData,
  VideoQuality? videoQuality,
})
```

When `from` is omitted, the connected Stringee user ID is used.

### Listener

```dart
StringeeListener(
  onConnected: (String userId) {},
  onDisConnected: () {},
  onRequestNewToken: () {},
  onConnectError: (int code, String message) {},
  onPresentCallWidget: (Widget callWidget) {},
  onDismissCallWidget: (String message) {},
  onReceiveCallInfo: (Map<dynamic, dynamic> info) {},
  onReceiveCustomMessage: (Map<dynamic, dynamic> message) {},
)
```

Register and remove the listener with:

```dart
await StringeeWrapper().addListener(listener);
StringeeWrapper().removeListener(listener);
```

## Repository safety

Do not commit:

- Stringee access tokens or API secrets
- Server private keys
- Signing keystores, passwords, provisioning profiles, or private APNs keys
- `pubspec_overrides.yaml` containing a developer-machine path

Firebase configuration files contain project identifiers and client API keys rather than Stringee
server secrets. Whether they are committed should still follow the owning Firebase project's
repository policy.
